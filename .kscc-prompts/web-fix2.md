# Agent Platform 单 Supervisor 交互、危险工具审批弹窗及界面重设计任务

## 一、任务目标

重新调整前端产品模型和视觉设计。

必须遵循以下真实业务关系：

```text
用户 → 系统 → 唯一 Supervisor → 内部 Agent → Tool
```

产品层面：

- 系统始终只有一个 Supervisor。
- 以后接入具体业务时仍然只有一个 Supervisor。
- 用户不知道 Supervisor、Agent 等内部编排概念。
- 用户登录后直接与“系统”对话。
- 页面不得让用户选择 Supervisor。
- 页面不得展示 Supervisor 技术名称，例如 `general_supervisor`。
- 页面不得展示 Agent 列表、Agent 选择器或“切换 Agent”。
- 前端仍通过真实 Supervisor 接口发送消息，但这是内部实现细节。
- 危险工具需要审批时，立即弹出审批弹窗。
- 用户关闭审批弹窗后，该审批仍保留在“待审批”页面中。
- 整体界面参考指定图片进行重设计。

# 三、单 Supervisor 产品模型

## 3.1 删除所有 Supervisor 选择行为

必须删除普通用户界面中的：

- Supervisor 选择器
- Supervisor 下拉菜单
- Supervisor 切换按钮
- “请选择 Supervisor”
- `general_supervisor` 等内部名称
- Supervisor 数量判断
- 多 Supervisor 选择分支
- Agent/Supervisor 模式切换
- Agent 列表和 Agent 选择入口

不要因为后端列表接口返回一个 Supervisor，就先显示选择页面。

## 3.2 登录后的行为

登录成功后：

1. 加载系统唯一的 Supervisor 配置。
2. 自动在内部确定唯一 Supervisor。
3. 直接进入聊天页面。
4. 用户可以立即输入消息。
5. 页面只显示产品名称或“智能协作助手”，不得显示 Supervisor 技术名称。
6. 不自动发送欢迎请求。
7. 不生成虚假的助手回复。

如果 Supervisor 正在加载：

- 显示轻量加载状态。
- 暂时禁用发送按钮。
- 不显示选择界面。

如果没有可用 Supervisor：

```text
智能协作服务暂时不可用，请稍后重试。
```

并提供“重新加载”按钮。

如果返回多个 Supervisor：

- 视为服务端配置异常。
- 不让用户选择。
- 不擅自选择第一个。
- 显示安全的服务不可用提示。
- 不暴露返回的 Supervisor 名称。

## 3.3 前端调用链

生产前端唯一聊天调用链必须是：

```text
ChatView
  → Chat Store
  → ChatTransport
  → Supervisor API
  → HTTP Client
  → /api/supervisor/invoke
```

不得调用：

```text
/api/agent/invoke
```

不得删除后端用于测试 Agent 的接口，本次只修改前端。

## 3.4 用户界面措辞

统一使用面向用户的产品语言：

- “智能协作助手”
- “新建对话”
- “输入消息”
- “正在处理”
- “等待审批”
- “执行完成”
- “执行失败”

不得出现：

- `general_supervisor`
- Supervisor ID
- Agent 名称
- 成员 Agent
- RunContext
- 节点名称
- 内部 Prompt
- 完整 metadata
- 内部工具参数
- Java 类名

# 四、危险工具审批弹窗

## 4.1 自动弹出

当真实 Supervisor 调用结果进入等待审批状态，或响应中包含经过验证的审批信息时：

- 立即弹出审批 Dialog。
- 必须使用现有 Reka UI Dialog。
- 不得使用 `window.confirm`。
- 不得使用假审批数据。
- 必须使用真实 `approvalId` 和真实审批 API。
- 展示内容只能来自后端允许暴露的安全字段。

弹窗至少展示：

- 标题：`需要你的确认`
- 操作名称
- 风险等级
- 安全的操作说明
- 请求时间（后端提供时）
- “同意”按钮
- “拒绝”按钮
- 右上角关闭按钮

不得展示：

- Session ID
- 用户权限
- 原始工具参数
- 密码或密钥
- 完整 metadata
- 内部调用栈
- 完整状态数据
- Agent 内部名称

## 4.2 同意

用户点击“同意”后：

1. 禁用重复操作。
2. 显示明确的处理中状态。
3. 调用真实审批恢复接口。
4. 成功后关闭弹窗。
5. 刷新待审批列表。
6. 将结果正确更新到当前聊天。
7. 如果恢复后的执行仍需新的审批，应针对新的 `approvalId` 再次弹窗。
8. 失败时保留弹窗和审批数据，并展示安全错误信息。

## 4.3 拒绝

点击“拒绝”后：

- 在当前弹窗内展开拒绝原因输入区，或进入同一个 Dialog 的拒绝确认状态。
- 拒绝原因必须填写。
- 去除首尾空格。
- 遵守后端 DTO 长度限制。
- 确认后调用真实拒绝接口。
- 成功后关闭弹窗并刷新待审批列表。
- 失败时保留输入内容，允许重试。

## 4.4 点击关闭按钮

点击右上角 `×`、按 Esc 或点击允许关闭的遮罩时：

- 只关闭当前弹窗。
- 不得自动同意。
- 不得自动拒绝。
- 不得调用审批接口。
- 不得删除审批。
- 不得把审批标记成已处理。
- 审批必须继续显示在“待审批”页面。
- 当前聊天可以显示轻量提示：`操作等待你的审批`。
- 关闭后不能阻塞页面其他导航操作。

同一个已经被用户关闭的审批弹窗，不应因组件重新渲染而反复自动弹出。

建议按 `approvalId` 记录本次前端会话中已关闭的弹窗状态，但：

- “待审批”页面始终以服务端真实数据为准。
- 不得把前端 dismissed 状态当作审批完成。
- 审批完成后应清理对应 dismissed 状态。

## 4.5 待审批页面

待审批页面必须继续支持：

- 查看全部真实待审批项。
- 同意。
- 拒绝并填写原因。
- 操作失败后保留当前审批项。
- 操作成功后刷新列表。
- 不同审批项状态互不干扰。
- 刷新页面后仍能从服务端重新获得未处理审批。

聊天弹窗与待审批页面必须复用同一套审批 API 和 Query Key，禁止实现两套不一致的审批逻辑。

# 五、界面重设计

## 5.1 整体布局

参考图片实现双栏聊天布局：

```text
┌──────────────────┬─────────────────────────────────────┐
│ 左侧导航与历史记录 │ 顶部会话信息                         │
│                  ├─────────────────────────────────────┤
│                  │                                     │
│                  │ 对话消息区域                         │
│                  │                                     │
│                  ├─────────────────────────────────────┤
│ 用户信息与退出     │ 固定输入区                           │
└──────────────────┴─────────────────────────────────────┘
```

桌面端左侧栏建议宽度约 `280px～320px`，具体以现有设计系统和实际显示效果为准。

视觉要求：

- 浅色、干净、克制。
- 使用柔和的灰白背景。
- 细边框。
- 小范围柔和阴影。
- 圆角卡片。
- 充足留白。
- 主要内容最大宽度受控。
- 不要大面积高饱和颜色。
- 不要把所有内容都包成厚重卡片。
- 不使用 emoji 作为功能图标。
- 图标统一使用项目当前 Lucide Vue 图标库。

## 5.2 左侧栏

左侧栏包含：

- 产品标识，例如“智能协作”。
- “新建对话”按钮。
- 按日期分组的会话历史。
- 当前会话高亮。
- 待审批入口，并显示真实待审批数量徽标。
- 用户有权限时显示用户管理、角色管理。
- 主题切换。
- 当前用户信息。
- 退出登录。

会话历史可分组为：

- 今天
- 昨天
- 更早

不得：

- 展示 Supervisor 名称。
- 展示 Agent 名称。
- 提供 Agent/Supervisor 切换。
- 使用固定的假历史记录。

如果后端没有历史会话查询接口，只展示当前前端生命周期内真实创建的线程，并在代码和最终输出中明确说明限制。

## 5.3 顶部区域

顶部栏显示：

- 当前会话标题。
- 系统可用时显示绿色状态点和“服务可用”。
- 加载中显示“正在连接”。
- 服务异常显示“暂不可用”。

不得显示：

- `general_supervisor`
- “切换 Agent”
- “切换 Supervisor”
- 内部执行单元名称

会话标题来自用户首条消息的安全截断版本，或使用“新对话”。

## 5.4 消息区

用户消息：

- 靠右显示。
- 使用淡紫色或淡蓝紫色背景。
- 圆角气泡。
- 显示时间。
- 与参考图保持相似的视觉层次。

系统回复：

- 靠左显示。
- 使用白色或接近白色的内容区。
- 左侧使用统一的系统头像图标。
- Markdown 排版清晰。
- 段落、列表、引用和代码块间距合理。
- 不显示内部 Supervisor 名称。

代码块：

- 保持 Markdown 原始顺序。
- 有语言标签。
- 有复制按钮。
- 复制成功和失败都有明确反馈。
- 未知语言安全回退。
- 代码区可以横向滚动。
- 不允许 XSS。

工具执行信息：

- 使用参考图中的紧凑工具状态卡片。
- 仅展示允许用户看到的工具名称或业务操作名称。
- 显示成功、失败、等待审批等状态。
- 可展示安全耗时。
- 默认折叠安全摘要。
- 不展示原始参数、完整结果或内部 Agent 名称。

## 5.5 输入区

输入区固定在聊天区域底部，参考图片实现：

- 大圆角输入容器。
- 输入框支持多行自适应。
- Enter 发送。
- Shift+Enter 换行。
- 发送按钮位于右下侧。
- 运行时显示取消等待按钮。
- 取消只能表示前端停止等待，不得宣称服务器执行已终止。
- 输入框上方不能被消息遮挡。
- 底部显示简短提示：

```text
内容由 AI 生成，请仔细甄别
```

附件、礼物、联网等当前不存在真实功能的图标不得照搬。没有真实能力就不要显示。

## 5.6 移动端

移动端必须：

- 左侧栏改为 Reka UI Sheet。
- 默认关闭。
- 使用菜单按钮打开。
- 支持 Esc、遮罩和关闭按钮。
- 不出现横向页面溢出。
- 消息气泡适配窄屏。
- 代码块内部横向滚动。
- 输入框不会被侧边栏或底部遮挡。
- 审批 Dialog 在窄屏内完整可操作。
- 同意、拒绝和关闭按钮均易于点击。

# 六、保留并复核之前的关键修复

不得因本次 UI 重构破坏以下功能：

1. `errorCode: null` 必须能通过 Supervisor 响应 Schema：

```ts
errorCode: z.string().nullable().optional()
```

2. Markdown 代码块必须保持正文中的原始位置。

3. 取消旧请求后立即发送新请求，不得让旧请求覆盖新请求状态或 AbortController。

4. 401 和主动登出必须清理：

- Query Cache
- 用户状态
- 聊天状态
- 会话索引
- Session

5. API 成功响应和错误响应必须经过 Zod 校验。

6. 不得出现宽松且无效的 E2E 断言。

7. Shiki 只能打包实际支持的语言和主题，不能通过提高警告阈值隐藏大分块问题。

8. 前端不得调用 `/api/agent/invoke`。

必须区分：

- Supervisor 配置加载中
- 服务可用
- 服务不可用
- 消息提交中
- Supervisor 处理中
- 前端已取消等待
- 等待人工审批
- 审批处理中
- 执行成功
- 执行失败
- 网络错误
- 响应格式错误

禁止用同一个 boolean 表达全部状态。

浏览器存储中的数据必须使用 Zod 校验后才能恢复。

不得在前端保存：

- 密码
- API Key
- Session ID 到 URL 或请求 Body
- 权限集合的持久化副本
- 原始审批参数
- 完整模型响应
- 内部 metadata
